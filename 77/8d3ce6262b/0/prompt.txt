# Noevu Plan

Create a structured implementation plan. **Do not write code in this step.**

Write plans assuming the implementer has zero context for the codebase. Document everything needed: which files to touch, what changes, how to test, how to verify. Give the whole plan as bite-sized tasks.

## Workflow

### 1. Input clarity

- If a recent brainstorm exists in `docs/brainstorms/`, use it as the starting point
- Otherwise clarify missing constraints briefly (don't re-brainstorm)

### 2. Mandatory research

Run before writing anything:
- `researcher` subagent — existing patterns, similar features, architectural constraints
- `~/.aiglobal/LEARNINGS.md` — past learnings relevant to this work
- `docs/solutions/` — solved problems in the same area

### 3. Consolidate findings

- Existing implementations and reusable patterns (exact file paths)
- Constraints from project rules
- Risks: security, data integrity, SEO, i18n, schema migrations

### 4. Write plan file

Save to `docs/plans/YYYY-MM-DD-<type>-<topic>-plan.md`

### 5. Plan structure (required)

Every plan MUST include:

```markdown
# [Feature Name] Implementation Plan

**Goal:** [One sentence]

**Architecture:** [2-3 sentences about approach]

---

### Task N: [Component Name]

**Files:**
- Create: `exact/path/to/file.ext`
- Modify: `exact/path/to/existing.ext` (what changes)
- Test: `tests/path/to/test.ext` (if applicable)

**Steps:**
1. [Specific action with exact file path]
2. [Verification command + expected output]
3. [Commit message]

### Acceptance Criteria
- [ ] [Testable assertion]

### Test Strategy
- [What to validate, how, where]

### Reference Implementations
- [Exact file paths to existing patterns being followed]
```

### Task granularity

Each task should be one coherent change (5-15 minutes of work):
- touching 1-3 files
- with a clear verification step
- committable independently

### Content rules for plan tasks

- **Exact file paths** — never "the relevant file"
- **Specific changes** — never "add validation" without showing what
- **Verification commands** with expected output
- **DRY, YAGNI** — don't plan abstractions for hypothetical future needs

### 6. Handoff

After saving the plan, recommend the appropriate next step:

- **`/noevu-plan-review` first** (default) — when the plan touches 3+ files, involves architectural decisions, has ambiguous acceptance criteria, or the user hasn't confirmed requirements
- **`/noevu-work` directly** — when the plan is small (1-2 tasks), the user explicitly said "just do it", or this is a second iteration after review feedback was already addressed

When unsure, recommend review first. The cost of reviewing is low; the cost of implementing the wrong plan is high.

## Stack-specific planning checks

Before finalizing, verify the plan accounts for:
- Astro route/content flow impacts (does a new page need a route? content file?)
- Zod schema updates + parser usage (`*.parse`) — new fields need schema changes
- component-map + section/component compatibility
- i18n/hreflang implications (`normalizeLocale`, locale paths, hreflang tags)
- CSS token/theme consistency (no hardcoded values, theme-aware)
- structured data updates for SEO-sensitive pages
